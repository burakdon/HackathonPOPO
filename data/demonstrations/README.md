# Demonstrations: demonstrator A (fictional, mock preferences)

`demonstrator_a_v1.jsonl`: 35 decision situations from a fictional practice session, each with the
decision context the model receives at inference, the valid options, the preferred action, and the
accepted actions used for evaluation. Generated by `uv run python -m training.build_demonstrations`.

**Provenance.** Team-authored fictional scenarios. The preferred actions were drafted by an AI
assistant from the written strategy below and are marked `review_status: pending human review`. A
teammate should read the file and change any preference that does not match the intended
demonstrator before results are presented. They are **not** clinician-validated treatment knowledge.

## Demonstrator A's strategy (one consistent approach)

After each confirmed attempt, in this order:

| rule | situation | preferred decision |
|---|---|---|
| A | correct, no hint, answered in at most 4 s | new picture, one tier harder (same tier at tier 3) |
| B | correct, no hint, slower than 4 s | new picture, same tier |
| C | correct after a hint | new picture, same tier |
| G | incorrect and the session has run 20 min or more | new picture, one tier easier (instead of a hint) |
| F | incorrect after two hints on this picture (or the attempt limit is reached) | new picture, one tier easier |
| D | first incorrect attempt on this picture | retry with the hint matched to the error: sound error → first sound; meaning error → description (semantic); no response or unidentified error → sentence to complete |
| E | incorrect after one hint, first sound not given yet | retry with the first sound |
| E-alt | incorrect after one hint, first sound already given | retry with a sentence to complete (preferred) or a description (also accepted) |

Hard constraints (enforced for every model, never learned): at most 3 attempts per picture; tier
moves by at most one step; only clinician-approved hints (`configs/clinical.yaml`). A preference
never changes a constraint.

## Splits

- 35 situations, one per scenario family (`family_id`), split by family **before** generation; no
  variants or paraphrases are made, so no test situation is a rewording of a training one.
- train 20, dev 5, test 10. The current picture of every test situation (kangaroo, glasses, apple,
  cactus, rabbit, key, helicopter, pretzel, tree, umbrella) is never the current picture in train or
  dev (checked by `tests/test_demonstrations.py`).
- Test labels are only read by `evaluation/compare.py`. Training uses `split == "train"`; the few-shot
  prompted baseline puts the 20 training situations in its prompt; dev is for checking settings.
- Rule coverage: train covers every rule; test exercises A, B, C, D (sound, unidentified), E-alt, F and G
  in situations not seen in training.

These counts are hackathon planning numbers, not an established data requirement. Ten test
situations are a small exploratory check, not a statistical or clinical validation.

Captured clinician examples from the app go to `runs/demonstrations/captured.jsonl` (gitignored) with
the same context format; they are pending until a training run lists their IDs in its manifest.

## v2: more training situations (`demonstrator_a_v2.jsonl`)

Generated by `uv run python -m training.build_demonstrations --v2`. The 35 v1 rows are kept
unchanged (dev and test byte-identical), plus 99 generated training situations (families
G001-G099, 9 per rule variant), giving 119 training situations with 10 to 12 per rule variant.
Provenance: generated from the written strategy above, `review_status: pending human review`.
The current picture of a generated situation is never the current picture of any dev or test
situation (stricter than v1, which only excludes test pictures), so none duplicates or rewords
a held-out one (`tests/test_demonstrations_v2.py`). The few-shot prompted baseline keeps the 20
v1 training situations in its prompt.
